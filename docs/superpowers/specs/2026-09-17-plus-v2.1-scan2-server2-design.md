## 1. Scan v2

### 1.1 Why the current scan is slow and its speeds are not trustworthy

One phase: every IP gets TCP → N delays → download → upload, with ONE concurrency for all of it,
batches of 20 IPs per throw-away core run one after another, engines one after another. Eight
downloads in flight share the owner's ~3 MB/s link, so every per-IP speed is a fraction of the truth;
a live IP costs 15–20 s; 100 IPs × 2 engines take minutes; the user sees no phase and no ETA.

### 1.2 Design: two phases, each with its own concurrency

**Phase 1 — filter (غربال).** Every IP on every selected engine: direct TCP connect to `ip:port`
(`tcpTimeout`, default 2000 ms), then `delaySamples` HTTP probes through the core (default 2,
`delayTimeout` 4000 ms). Cheap, so it runs wide: `filterConcurrency` probes in flight per core
(default 16, 1–64) and `coresInParallel` throw-away cores at once (default 2, 1–6) — batches of
`batch` IPs (default 20) are scheduled through one `pLimit(coresInParallel)` shared by all engines,
so engines run side by side instead of one after another. A dead IP ends at the TCP step; a live
one yields `delay = { min, median, avg, jitter, loss, samples }` (median added: one slow sample must
not sink a good IP).

**Phase 2 — speed (سرعت).** Only the best `speedTop` IPs of phase 1 **per engine** (default 10,
0 = skip the phase) get the download (and, when ticked, the upload). Throughput is only meaningful
when downloads do not share the link, so `speedConcurrency` defaults to **1** (1–4), and
`speedRounds` (default 1, 1–3) repeats the download and keeps the best round. The download reports
`ttfb`, and `mbps` measured from `warmupMs` (default 300) after the first byte to the last byte —
the slow-start ramp is excluded — over at most `downMaxMs` (default 6000) or `downBytes` (10 MB).

**Ranking.** `score` as today but on the **median** delay; rows that did not reach phase 2 keep the
delay-only score. Result rows carry `phase: 1|2` so the table can show which numbers are final.

**Presets** (renderer): *سریع* (filter only: `delaySamples 1`, `tcpTimeout 1500`, `delayTimeout 3000`,
`filterConcurrency 32`, `coresInParallel 3`, `speedTop 5`), *متعادل* (the defaults above), *دقیق*
(`delaySamples 4`, `filterConcurrency 8`, `speedTop 20`, `speedRounds 2`, `speedConcurrency 1`).
Choosing a preset fills the fields; the fields stay editable.

**Progress.** `scan-progress` events carry `stage: 'filter' | 'speed' | 'done'`, `done`, `total`,
`alive` (IPs that passed phase 1), `speedDone`, `speedTotal`, and `etaMs` (from the measured rate of
the current stage). The tab shows the stage, the counters, a bar per stage and the ETA; *Stop* works
in either stage; *re-test the top N* runs phase 2 alone on the chosen rows.

**Decision:** speeds are measured through the config, against `speed.cloudflare.com` by default
(both `__down` and `__up` answer our probe's user agent with 200 — verified 2026-09-17). Engines
still test the same IPs so the two cores can be compared row by row.

### 1.3 Interfaces

```js
// scanner.js
runScan({ server, ips, engines, tests, opts, xray, onResult, onProgress, token })
opts: { batch, filterConcurrency, coresInParallel, delaySamples, tcpTimeout, delayTimeout,
        speedTop, speedConcurrency, speedRounds, warmupMs, downBytes, downMaxMs, downHost, downPath, downPort, downTls,
        upHost, upPath, upPort, upTls, upBytes, upTimeout, probes?, getFreePorts? }
// result: { ip, engine, phase: 1|2, tcp, delay: { min, median, avg, jitter, loss, samples }, down, up, score, error }
// onProgress: { stage, done, total, alive, speedDone, speedTotal, etaMs }
// probes.js: downloadThroughProxy(port, { ..., warmupMs }) → { ok, bytes, ms, ttfb, mbps, error }
// index.js: scan:start accepts opts above (legacy `concurrency` is read as filterConcurrency);
//           scan:presets → { cfRanges, defaults, presets: { fast, balanced, accurate }, last, engines }
//           scan:retest { serverId|link, rows: [{ ip, engine }], opts } → phase 2 only, same events
```

## 2. Server v2 — the 3x-ui model

### 2.1 What "like 3x-ui" means here

3x-ui v3.8.5 (Xray-core 26.9.9): a table of **inbounds** (enable, remark, protocol, port, clients,
traffic, expiry), each with a **tag** (`inbound-<port>`) and **clients** carrying email, id/password,
flow, limit IP, total GB, expiry, reset cycle, comment, enable — and, for VLESS, a **reverse** config
on the client (v3.8.5: "a vless client carrying a reverse config keeps its tunnel across an edit").
Xray settings are edited as **outbounds with tags** and **routing rules** that reference those tags.
Plus keeps the app-shaped things it already has (a local core it starts itself, per-user meters from
`/debug/vars`, share links, the Windows firewall button) and adopts that model and that layout.

### 2.2 Model v2 (store key `xserver`, `schema: 2`; v1 is migrated on first read, never in place)

```js
{
  schema: 2,
  autoStart, engine, logLevel, publicAddress,
  inbounds: [{
    id, tag,                          // editable; default 'inbound-<port>'; unique among every tag in the model
    enabled, remark, protocol, listen, port, network, path, host, serviceName, security, tls, reality, ss, sniffing,
    totalBytes: 0, expiresAt: 0,      // inbound-level quota and expiry (3x-ui "total" / "expiry time"); 0 = none
    used: { up, down },               // lifetime meter of the inbound (from stats.inbound.<tag>)
    clients: [{
      id, enabled, email, uuid, password, flow,
      limitIp: 0,                     // informational: the core cannot enforce it without its API (said in the form)
      quotaBytes: 0, expiresAt: 0,
      resetDays: 0, resetAt: 0,       // quota reset cycle: when now ≥ resetAt, used = 0 and resetAt += resetDays (enforcer)
      comment: '',                    // v1 `note`
      reverseTag: '',                 // VLESS only: this client is a bridge's credential; its value is the outbound tag a
                                      // routing rule sends user traffic to — xray's `clients[].reverse.tag`
      used: { up, down }, disabledBy, lastSeenAt: 0
    }]
  }],
  outbounds: [{ id, tag, kind: 'freedom' | 'blackhole' | 'server' | 'link', serverId: '', link: '',
                reverseTag: '',       // VLESS server/link only: this outbound dials a portal; reversed connections arrive
                                      // as an inbound with this tag — xray's outbound `settings.reverse.tag`
                enabled: true }],
  routing: {
    domainStrategy: 'IPIfNonMatch',
    rules: [{ id, enabled, comment, inboundTags: [], outboundTag, domain: [], ip: [], port: '', protocol: [], network: '',
              preset: '' | 'private' | 'torrent' | 'ads' }]
  }
}
```

Xray semantics carried as-is: **rule order is the array order**, the first enabled outbound is the
default exit, `inboundTags` may name an outbound's `reverseTag` (the bridge side), `outboundTag` may
name a client's `reverseTag` (the portal side).

**Migration from v1** (`migrateModel`): `exit.direct` → outbounds `[direct: freedom, block: blackhole]`;
`exit.server` → `[exit: server(serverId), block]`; `blockPrivate` → a `preset: 'private'` rule
(`ip: ['geoip:private']` → `block`); `blockTorrent` → `preset: 'torrent'` (`protocol: ['bittorrent']`
→ `block`); v1 bridge → outbound `{ tag: 'interconn', kind: via, reverseTag: 'bridge' }` + rule
`{ inboundTags: ['bridge'], outboundTag: 'direct' }`; v1 portal → the interconn inbound's enabled
clients get `reverseTag: 'portal'` and a rule `{ inboundTags: userTags, outboundTag: 'portal' }`; v1
`note` → `comment`; v1 tags (`vless-reality-a1b2`) are kept, new inbounds get `inbound-<port>`.

### 2.3 Config generation (`config.js`, still pure)

- Inbounds as in v2.0 plus `clients[].reverse = { tag }` where `reverseTag` is set.
- Outbounds in list order: `freedom` (+ `finalRules: [{ action: 'allow' }]` when any outbound in the
  model carries a `reverseTag` — this machine is a bridge and the 26.9 core blackholes reversed
  destinations otherwise), `blackhole`, `server`/`link` cloned with `cloneOut`/`applyFragments` as
  today, and in the flat VLESS form with `settings.reverse.tag` when `reverseTag` is set.
- Routing: enabled rules 1:1 (empty fields omitted), `domainStrategy`.
- Validation (`validateModel`): every tag unique across inbounds, outbounds and client reverseTags;
  reserved names (`metrics`, `api`) refused; a rule's `outboundTag` must be an enabled outbound tag
  or an enabled VLESS client's `reverseTag`; its `inboundTags` must be inbound tags or outbound
  reverseTags; at least one enabled outbound; `reverseTag` only on VLESS clients / VLESS outbounds;
  port collisions per listen address (3x-ui v3.8.5 refuses these at save); the rest as v2.0.
- `clientLink`, `clientServerRecord`, `otherSideSnippet` (now from tags: for every client with a
  `reverseTag` → the bridge side's outbound + rule; for every outbound with a `reverseTag` → the
  portal side's inbound client with `reverse.tag` + the rule placeholder) and two **wizard helpers**
  the UI calls through `xserver:wizard`:
  - `wizardPortal(model, { inboundId, clientId, userInboundIds, tag = 'bridge-1' })` → sets the client's
    `reverseTag`, inserts `{ inboundTags: userTags, outboundTag: tag, comment: 'reverse → <tag>' }` before
    the first rule that would catch those inbounds (or at the end), returns `{ model, link }`.
  - `wizardBridge(model, { link | serverId, exitOutboundTag = first freedom, tag = 'interconn', reverseTag = 'bridge' })`
    → appends the outbound, appends `{ inboundTags: [reverseTag], outboundTag: exitOutboundTag }`, returns `{ model }`.

### 2.4 Runtime (`core.js`, `index.js`)

- The tick also meters inbounds (`stats.inbound.<tag>`) into `inbound.used`, stamps
  `client.lastSeenAt` when a counter moves (`online` = moved in the last tick, as today), applies
  `resetDays`, and enforces inbound `totalBytes`/`expiresAt` (an inbound that ran out is disabled with
  `disabledBy`, same debounced restart).
- Status adds `tag`, `disabledBy`, `used` per inbound and `lastSeenAt`, `reverseTag` per client.
- Channels: `xserver:get/set/start/stop/restart/status/log/genKeys/genId/clientLink/preview/otherSide/firewall`
  as today, plus `xserver:wizard { kind: 'portal' | 'bridge', ...args }` → the helpers above applied
  through `applyModel`, and `xserver:coreInfo` → `{ engine, version, channel, latestStable, latestAny }`.
- **Core channel.** New setting `coreChannel: 'stable' | 'latest'` (default `stable`) in both
  `DEFAULT_SETTINGS` (hook lines). The downloader's `releaseApiUrl(engineId, channel)` returns
  `/releases?per_page=5` for `latest`, and the release picker takes the first non-draft entry
  (pre-releases included) — three marked lines in `downloader.js`; `assetUpdater.latestVersion`
  follows the channel. The server tab's Settings sub-tab shows the running core version, the channel
  and a "get the latest core" button that calls the existing `assets:download`.

### 2.5 UI v2 (`src/renderer/plus/xserver.*`, `#view-xserver`) — a rewrite

Sub-tabs across the top of the view: **نمای کلی · ورودی‌ها · خروجی‌ها · روتینگ · ریورس · تنظیمات · لاگ**.

- **نمای کلی**: state pill, uptime, core + version, totals up/down, clients online / total, Start /
  Stop / Restart, the last error.
- **ورودی‌ها**: a **table** — enable, remark, protocol badge, `listen:port`, tag, clients (n · online),
  traffic, quota/expiry, actions (edit, clients, links/QR, firewall on Windows, delete). A row
  expands into the **clients table** — enable, email, secret (masked, click to copy), flow, limit IP,
  quota bar, expiry, reset, comment, reverse-tag badge, online dot, link, QR, edit, delete. "+ ورودی"
  and "+ کاربر" open modals with exactly the 3x-ui fields (client: email, id/password + generate,
  flow, limit IP, total GB, expiry date, reset days, comment, enable, and for VLESS a "reverse tag"
  field with the one-line explanation).
- **خروجی‌ها**: table — enable, tag, kind/target, reverse tag, actions; add: مستقیم (freedom),
  مسدود (blackhole), از کانفیگ‌های من (picker), از لینک (paste).
- **روتینگ**: the ordered rules table — enable, inbound tags, outbound tag, domain, ip, port,
  protocol, network, comment, ▲ ▼, delete; "+ قانون" modal; preset buttons (block private, block
  torrent, block ads) that add the preset rules once; `domainStrategy` select.
- **ریورس**: two cards, "این دستگاه portal است" (choose the VLESS inbound, the bridge's client,
  the user inbounds → runs `wizardPortal`; shows the link the bridge pastes and "copy the other
  side") and "این دستگاه bridge است" (paste the portal's link or pick a config, choose the exit →
  `wizardBridge`). Underneath, a read-only list of every reverse tag in the model with the rules
  that use it, each linking to the Routing tab. What the wizards write is ordinary outbounds and
  rules, visible and editable there — "با تگ".
- **تنظیمات**: engine, core channel + version + "get the latest core", log level, public address,
  start with the app, domain strategy.
- **لاگ**: the ring, following.

Persian first; every string from `xserver.i18n.js`; tokens, logical properties, no inline styles;
`[hidden]`; every id in `index.html`; the contract and syntax tests cover the files.
